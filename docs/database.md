# База данных, миграции и демонстрационные данные

## Хранилище и tenant boundary

Схема хранится в `supabase/migrations/*.sql` и применяется по timestamp-порядку. Данные принадлежат школе через `school_id`; связи и API должны предотвращать пересечение школ. Ключевые таблицы: `schools`, `users`, `roles`, `user_roles`, `academic_years`, `classes`, `subjects`, `terms`, `students`, `enrollments`, `grades`, `behavior_criteria`, `behavior_sheets`, `behavior_scores`, `behavior_permissions`, `attendance_records`, `invites`, `refresh_sessions`, `audit_log`.

Схема описывает структуру; API-логика применяется поверх неё. RLS и backend authorization не взаимозаменяемы: тестируйте доступ HTTP API через роли.

## Миграции

- Начальная схема: `20261028182451_initial_school_journal_schema.sql`.
- Tenant integrity и расчёт полноты поведения: `20261028182519_tenant_integrity_and_behavior_status.sql`.
- Демонстрационная миграция `20261101125020_demo_school_data.sql` намеренно no-op, не создаёт публичные demo accounts.
- Таблица дневной посещаемости: `20261101140000_attendance_register.sql`.
- Идемпотентные стандартные criteria для школ без criteria: `20261101150000_default_behavior_criteria.sql`.

Перед применением новой миграции:

1. Проверить diff SQL, совместимость с уже существующей схемой и все DDL/DML.
2. Создать и проверить восстановление backup.
3. Применить сначала к disposable/local, затем staging/QA, выполнить тесты и сверку.
4. Согласовать production окно и rollback. Применение production миграций требует отдельной явной операции/одобрения; сам факт наличия файла не означает, что БД обновлена.
5. После применения проверить version/status миграций и read-only schema/data checks.

Миграции обратимы не всегда. Не выполняйте `db reset` или деструктивный DDL на общей/production базе. Учитывайте, что backend deploy может не применять миграции автоматически.

## Критерии поведения и Excel

Генерация ведомости и её экспорт требуют ровно 10 критериев текущей школы. `behavior_criteria` содержит school-specific `code`, `title`, `max_score`, `sort_order`. Spreadsheet заголовки поведения динамически формируются из кодов, а UI из названий; не редактируйте коды и порядок без согласованной миграции и адаптации данных.

Стандартная миграция для пустых школ вставляет значения только когда у школы нет ни одного критерия; custom/existing конфигурацию сохраняет. На неполной конфигурации из 1–9 критериев миграция не «дополняет» записи частично; администратор должен исследовать конфигурацию и восстановить согласованный шаблон. До применения к production требуется отдельная оценка существующих данных.

## Локальные demo fixture

`supabase/seed.sql` содержит публично известные тестовые пароли и реалистичный фиктивный набор. Он предназначен только для отдельной локальной disposable базы. Полный набор включает школу, роли пользователей, академические годы/периоды/классы, предметы, фиктивных учеников, оценки, criteria, ведомости и другие демонстрационные связи.

Скрипт `scripts/validate-demo-seed.sh` требует `DATABASE_URL`, прогоняет SQL migrations и seed, затем проверяет количества и demo credentials. Скрипт **пишет** в базу; он не умеет надёжно определять, является ли DSN production. Запускать только с изолированной базой, никогда не с production.

Рекомендованный порядок на отдельной disposable базе:

1. Создать пустую локальную PostgreSQL/Supabase БД.
2. Назначить её DSN как `DATABASE_URL` и визуально проверить host/database.
3. Выполнить `bash scripts/validate-demo-seed.sh`.
4. Указать ту же изолированную базу как `TEST_DATABASE_URL` и запустить API integration test.
5. После работы удалить/recreate только disposable БД.

Команда `supabase db reset` пересоздаёт БД. Используйте только если доказано, что CLI связан с локальным проектом. Проверьте `supabase status`, project ref и connection target перед любой reset. Никогда не используйте reset как способ загрузить тестовые данные в production.

Demo credentials перечислены в корневом README и доступны любому читателю репозитория; не публикуйте их в production, не используйте повторно реальные пароли, отключите/удалите demo users до ввода реальных данных.

## Backup и восстановление

Используйте поддерживаемый PostgreSQL/Supabase backup, зашифрованное хранилище и ограничение доступа. Регулярно проводите restore drill в отдельный staging проект. Backup содержит персональные/учебные данные и секреты, следовательно, должен быть защищён и иметь срок хранения. Конкретные команды зависят от инфраструктурного способа подключения и не включены намеренно, чтобы не допустить accidental overwrite/restore не в тот проект.
