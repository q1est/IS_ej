# Роли и функциональность

## Роли

| Роль | Назначение | Основной доступ |
|---|---|---|
| `student` | Ученик | Свои оценки, собственная ведомость поведения и собственные отметки посещаемости; без редактирования |
| `teacher` | Учитель-предметник | Только назначенные класс/предмет/учебный год; выставление оценок; ведомость поведения только при `can_score`; посещаемость назначенных классов |
| `class_teacher` | Классный руководитель | Назначенные классы, сводка оценок только для чтения, ведомость поведения класса и посещаемость назначенного класса |
| `admin` | Администратор школы | Школьное управление, пользователи, приглашения, справочники, полные школьные контексты оценок и посещаемости, генерация ведомостей поведения и аудит |

Администраторские полномочия проверяются отдельно. Роль `admin` сама по себе не должна трактоваться как роль `student`; если пользователь явно имеет обе роли, серверный административный приоритет исключает student-only ограничения. Создавайте отдельные пользовательские аккаунты для тестирования разных ролей.

## Функции по областям

### Аутентификация

- Вход — email и пароль.
- Публичной регистрации нет: аккаунт активируется по приглашению.
- Приглашение одноразовое, ограничено сроком действия; тестируйте его на изолированной базе.
- Refresh-токен ротируется; выход завершает refresh-сессию.
- Изменение статуса пользователя на disabled должно блокировать API и отзывать refresh-сессии.

### Учебная структура и ученики

Администратор поддерживает учебные годы, классы, предметы, периоды, учеников и зачисления. Журналы отображают учеников, зачисленных в выбранный класс/год и подходящих по датам/статусу. Наличие карточки ученика без зачисления не гарантирует появление в классном журнале.

### Оценки

- Учитель видит контексты своих назначений; администратор — школьные контексты.
- Ученик видит только собственные оценки.
- Учитель/администратор могут создавать и редактировать оценки согласно серверному праву.
- Повтор одной и той же работы может вернуть `409 conflict` — проверяйте уникальный ключ работы.
- Удаление оценки — мягкое удаление, запись остаётся в аудите/истории согласно реализации.
- Классный руководитель использует сводку без права предметного редактирования.

### Посещаемость

Дневная ведомость содержит активный список класса и отметки `present`, `absent`, `late`, `excused`, а также примечание. Пустое состояние может означать ещё не отмечено. Пакетное сохранение проверяет дату учебного года, членство ученика в классе, уникальность и допустимость каждой записи. Запись сохраняется с аудитом. Администратор редактирует записи по всем школьным классам.

### Ведомость поведения

- Для каждой школы должны быть настроены ровно 10 критериев; коды и названия динамически попадают в Excel.
- Администратор создаёт ведомости для активных учеников выбранного класса, года и периода.
- Учитель редактирует оценки только при разрешении `behavior_permissions.can_score` для соответствующего класса/года.
- Критерии оцениваются значениями 0–максимум (обычно 3). Незавершённость сохраняется отдельно от полного результата.
- Заполненный итог пересчитывается сервером; диапазоны вердикта определены backend-функцией.
- Desktop и mobile показывают одни и те же критерии; на узком экране таблицу можно прокручивать горизонтально.

### Excel

- Администратор скачивает workbook школы, редактирует справочники и импортирует файл.
- Названия листов, обязательные заголовки и идентификаторы справочников должны соответствовать текущему экспортному шаблону.
- Критерии поведения динамические: для листа ведомостей заголовки сопоставляются кодам критериев. Не переименовывайте коды без понимания последствий; сохраняйте Excel-шаблон, экспортированный текущей версией.
- Ошибка в строке должна сообщать лист и номер строки; импорт выполнять только в согласованное окно, предварительно сохранив экспорт/backup.
- Проверяйте результат импорта повторным экспортом и сверкой строк; не импортируйте непроверенный пользовательский файл в production.

### Администрирование и аудит

Админка управляет ресурсами, приглашениями, ролями/статусами, отзывом сессий и просмотром аудита. Ошибка одного API-запроса должна сопровождаться отдельным сообщением и не скрывать успешно загруженные разделы. Любой критичный сбой проверяйте в Network/Console и в серверных логах, не публикуя токены или персональные данные.
