# Электронный школьный журнал

Веб-приложение школьного журнала на Go, PostgreSQL/Supabase и ванильном JavaScript. Backend и frontend разделены: браузер вызывает только REST API и не подключается к Supabase напрямую.

## Архитектура

- `cmd/api` — запуск HTTP-сервера и graceful shutdown.
- `cmd/seedadmin` — безопасное создание первого администратора и 10 критериев поведения.
- `internal/auth`, `students`, `grades`, `behavior`, `admin` — независимые доменные модули.
- `internal/platform` — PostgreSQL, HTTP-ответы, конфигурация и rate limit.
- `internal/audit`, `internal/identity`, `internal/api` — аудит, идентификация и сборка приложения.
- `web/js` — отдельные модули API, интерфейса, журнала, поведения, администрирования и маршрутизации.
- `supabase/migrations` — версионируемая схема БД для Supabase.

## Быстрый запуск

1. Supabase-проект `school-journal` (`fmkudsrekkgfmiojhprt`) уже создан. Миграции находятся в `supabase/migrations` и применяются по порядку. Вторая миграция добавляет tenant-FK и стабильную привязку аккаунта ученика; она намеренно остановится на существующих неконсистентных или межшкольных связях.
2. Установите Go 1.23+. Настройте в терминале `DATABASE_URL`, `JWT_SECRET` (минимум 32 случайных байта), `ALLOWED_ORIGINS` (список origin через запятую) и при необходимости `PORT`. `.env.example` — образец переменных, Go сам не загружает `.env`.
3. Выполните `go mod download`, затем `go test ./...`.
   Для полного локального smoke-набора с PostgreSQL используйте `DATABASE_URL=... bash scripts/validate-demo-seed.sh`, а затем `TEST_DATABASE_URL=... go test ./internal/api -run TestDemoTeacherInvitationAssignmentAndGradeWorkflow -count=1 -v`.
4. Создайте первого администратора: `go run ./cmd/seedadmin --email admin@example.org --name "School Admin"`. Пароль вводится скрыто и должен содержать не менее 12 символов. Команда не сбрасывает пароль существующей учётной записи.
5. Запустите API командой `go run ./cmd/api`. Проверка готовности: `GET /healthz`.
6. Для локального запуска `web/config.js` автоматически использует `http://127.0.0.1:18081`; если API работает на другом порту, измените значение вручную. В production задайте HTTPS URL API через `NETRUN_API_URL`: Pages workflow перезапишет конфигурацию при публикации. Отдайте каталог `web` обычным статическим сервером; локально удобно использовать `python -m http.server 5500 -d web`. Добавьте origin этого сервера в `ALLOWED_ORIGINS`.

Docker-образ собирается многоступенчато, запускается от непривилегированного пользователя и проверяет `/healthz`. GitHub Pages публикует `web/`, а workflow `deploy-netrun.yml` синхронизирует backend с проектом Netrun.

### Netrun deployment

Пошаговая настройка находится в [`deploy/netrun/README.md`](deploy/netrun/README.md). Первый проект создаётся в кабинете Netrun из GitHub-репозитория. После этого успешное завершение `Go CI` для push в `main` запускает `.github/workflows/deploy-netrun.yml`, который загружает архив ровно проверенного commit. Устаревший запуск пропускается, если в `main` уже появился более новый commit.

В настройках самого проекта Netrun задаются `DATABASE_URL`, `JWT_SECRET` и `ALLOWED_ORIGINS=https://q1est.github.io`. В GitHub Actions нужны только `NETRUN_API_KEY` и числовой `NETRUN_PROJECT_ID`; архив не содержит `.env` и секретов.

## Основные сценарии

- Вход по email и паролю, одноразовые приглашения на 7 дней, refresh-сессии с ротацией и аудитом. Публичной регистрации нет.
- Ученик видит только собственные оценки и ведомость. Привязка к ученику хранится по ID, а не по ФИО.
- Учитель видит назначенные комбинации класса, предмета и периода; создаёт, редактирует и мягко удаляет оценки. Повторная оценка той же работы возвращает конфликт.
- Классный руководитель получает read-only сводку оценок и ведомость поведения своего класса.
- Учитель видит ведомость поведения только при явном разрешении `can_score` и может менять баллы только в рамках разрешения.
- Администратор управляет справочниками, зачислениями, назначениями, проектами и приглашениями; может завершить refresh-сессии пользователя и читать аудит.
- Учитель и классный руководитель отмечают ежедневную посещаемость по своим классам; ученик может просматривать собственные отметки. Изменения атомарны, ограничены учебным годом и записываются в аудит.
- Ведомости поведения хранят неполное состояние отдельно. Полный результат пересчитывается на сервере и атомарно записывается с аудитом; пустой балл можно очистить.
- Экспорт CSV сохраняет русские заголовки, разделитель `;`, и защищает текст от формул электронных таблиц.

## API

- Auth: `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `POST /invites/accept`, `GET /me`.
- Ученики: `GET /students`, `GET /students/{id}`.
- Оценки: `GET /grades/contexts`, `GET /grades`, `GET /grades/class-summary`, `POST /grades`, `PATCH /grades/{id}`, `DELETE /grades/{id}`.
- Поведение: `GET /behavior/contexts`, `GET /behavior/criteria`, `GET /behavior/sheets`, `POST /behavior/sheets/generate`, `GET /behavior/sheets/{id}`, `PATCH /behavior/sheets/{id}/scores`, `GET /behavior/sheets/{id}/export.csv`.
- Посещаемость: `GET /attendance/contexts`, `GET /attendance?class_id=...&date=YYYY-MM-DD`, `PUT /attendance` (пакетное сохранение отметок).
- Администрирование: `GET/POST /admin/{resource}`, `GET /admin/users`, `PATCH /admin/users/{id}`, `GET /admin/invites`, `POST /admin/invites/{id}/revoke`, `POST /admin/users/{id}/revoke-sessions`, `GET /admin/audit`, `POST /invites`.

Все защищённые маршруты повторно проверяют роль и школьную область на сервере. Ошибки используют формат `{ "code": "...", "message": "...", "details": null }`. API ограничивает тело JSON 1 MiB. Auth endpoints защищены in-memory rate limit; для нескольких экземпляров добавьте ограничение на reverse proxy.

## Перед production-запуском

Проверено в репозитории: миграции и повторяемый demo seed на PostgreSQL, вход/refresh, приглашение и активация учителя, назначение класса и предмета, CRUD оценок, конфликт дубликата, мягкое удаление, student-scope, изменение ролей и блокировка пользователя интеграционным API-тестом. Перед реальными персональными данными остаются внешние зависимости: security review, MFA администратора, доставка приглашений по email, резервное копирование и юридическая проверка требований к персональным данным. Не используйте demo-аккаунты в публичном production.

Репозиторий связан с GitHub: `https://github.com/q1est/IS_ej`. Deployment workflows не хранят секреты в коде и не публикуют `.env`.

Перед включением production отметьте все пункты:

- [ ] применены миграции в отдельной проверенной базе и создан backup с тестом восстановления;
- [ ] в Netrun заданы `DATABASE_URL`, `JWT_SECRET` и `ALLOWED_ORIGINS`, а в GitHub — `NETRUN_API_KEY`, `NETRUN_PROJECT_ID`, `NETRUN_API_URL`;
- [ ] включены MFA для администраторов и ограничение rate limit на reverse proxy;
- [ ] настроены email-приглашения и процесс отзыва доступа;
- [ ] проведены security review и проверка требований к персональным данным;
- [ ] demo-аккаунты удалены или заменены уникальными паролями.

Без отмеченных инфраструктурных пунктов приложение считается подготовленным к развёртыванию, но не введённым в эксплуатацию.

# Demo dataset

После применения миграций можно загрузить реалистичные данные для демонстрации и ручного тестирования:

```bash
supabase db reset
```

Создаются:

- школа «Сириус»;
- администратор `admin@demo-school.local` / `DemoAdmin2026!`;
- три учителя `math.teacher@demo-school.local`, `language.teacher@demo-school.local`, `class.teacher@demo-school.local` / `Teacher2026!`;
- два учебных года (2025/2026 и 2026/2027), четыре четверти в каждом;
- классы 6А и 7Б в прошлом году, перевод учеников в 7А и 8Б в текущем;
- шесть предметов, назначения учителей и классное руководство за оба года;
- десять учеников, двадцать зачислений и 320 оценок за прошлый и текущий периоды;
- роли, проекты и участие учеников, десять критериев поведения, двадцать ведомостей, баллы и права заполнения;
- заполненные приглашение, отозванная сессия и запись аудита для демонстрации истории.

Это демонстрационные аккаунты с публичными тестовыми паролями. Они создаются только явным локальным `supabase db reset` через `supabase/seed.sql`; production-миграция демо-данных намеренно является no-op и не создаёт публичные учётные записи.

Автоматические проверки также запускают `node --test web/js/api.test.mjs`: они проверяют восстановление сессии после обновления страницы и сохранение новой пары refresh/access токенов после ротации.

### Демо-данные и production

`supabase/migrations/20261101125020_demo_school_data.sql` оставлена в истории миграций как безопасная no-op, чтобы не изменять production через уже применявшийся workflow. Не включайте публичные демо-пароли в production. Для локальной разработки используйте только отдельную базу и явный `supabase db reset`, который пересоздаёт базу.
